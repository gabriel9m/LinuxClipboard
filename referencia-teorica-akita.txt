<a href="#o-mito-do-one-shot-prompt" class="subheading-anchor" aria-label="Permalink for this section"></a></h2><p>Tem uma narrativa crescente de que “vibe coding” é escrever uma spec detalhada, dar pro agente de IA, e ele entrega o sistema pronto. Tipo aqueles vídeos de “criei um SaaS em 10 minutos com o Cursor”. Nenhum spec do mundo prevê isso. <strong>O sistema correto emerge da iteração, não da especificação.</strong></p><h2>Pair Programming Com Um Agente de IA<span class="hx:absolute hx:-mt-20" id="pair-programming-com-um-agente-de-ia"></span>
<a href="#pair-programming-com-um-agente-de-ia" class="subheading-anchor" aria-label="Permalink for this section"></a></h2><p>Eu não uso o Claude Code como um gerador de código. Uso como um par de pair programming.</p><p>A diferença é fundamental. Um gerador de código recebe uma spec e devolve output. Um par de pair programming <strong>conversa</strong>. Eu interrompo quando ele toma um caminho errado. Dou contexto que ele não tem. Questiono decisões. Peço alternativas. Às vezes digo “para, isso tá ficando complicado demais” e ele simplifica.</p><p>Alguns exemplos reais dos 274 commits:</p><p><strong>Interrupção por excesso de engenharia.</strong> Quando pedi o sistema de email delivery, a primeira proposta tinha uma state machine com 8 estados, retry queues separadas, e dead letter handling. Interrompi: “Simplifica. Quatro estados: pending, sending, sent, unknown. Na dúvida, não reenvia.” O resultado foi o <code>SendSingleEmailJob</code> com a variável <code>ses_accepted</code> como pivô — 40 linhas que resolvem o problema inteiro.</p><p><strong>Contexto que o agente não tem.</strong> Quando estávamos no Yahoo Finance, o Claude tentou usar HTTParty. Expliquei: “Yahoo faz TLS fingerprinting, vai bloquear qualquer HTTP client que não seja browser real.” Resultado: headless Chromium com crumb authentication. Isso não está em nenhum tutorial — é o tipo de conhecimento que vem de tentar e falhar.</p><p><strong>Decisão de arquitetura conjunta.</strong> O podcast pipeline poderia ser um monolito Python. Sugeri: “Rails orquestra, Python serve TTS via HTTP, conteúdo integra por filesystem.” O resultado — <code>QwenTtsClient</code> no Ruby chamando <code>podcast-tts</code> em Python — mantém cada linguagem no que faz melhor.</p><p><strong>Prompt refinement iterativo.</strong> As primeiras newsletters saíam genéricas. Os comentários do Akita e do Marvin soavam iguais. Fui ajustando prompts com ele: “Akita nunca diz ’talvez’. Marvin usa ‘bom…’ e ’enfim’. O LLM vai suavizar opiniões se você não for explícito.” Cada ajuste era um commit de prompt, testado com dados reais.</p><p>O padrão é: eu trago o <strong>quê</strong> e o <strong>porquê</strong>. O agente traz o <strong>como</strong> — e o como é frequentemente melhor do que eu faria sozinho. Mas o como sem o quê produz código correto que resolve o problema errado. E o quê sem o como produz specs que nunca saem do papel.</p><h2>Extreme Programming Não É Moda dos Anos 2000<span class="hx:absolute hx:-mt-20" id="extreme-programming-não-é-moda-dos-anos-2000"></span>
<a href="#extreme-programming-n%c3%a3o-%c3%a9-moda-dos-anos-2000" class="subheading-anchor" aria-label="Permalink for this section"></a></h2><p><img src="https://new-uploads-akitaonrails.s3.us-east-2.amazonaws.com/frankmd/2026/02/agile-lifecycle-development-process-diagram-vector-31188796.jpg" alt="agile lifecycle development process diagram" loading="lazy"></p><p>Tudo que fizemos tem nome no XP. Não porque planejei — porque são as práticas que naturalmente emergem quando você programa com feedback rápido:</p><h3>Pair Programming<span class="hx:absolute hx:-mt-20" id="pair-programming"></span>
<a href="#pair-programming" class="subheading-anchor" aria-label="Permalink for this section"></a></h3><p>Já expliquei. O par é o agente. A dinâmica é a mesma: um pilota, outro navega. Eu navego mais do que piloto — defino direção, questiono decisões, corrijo rota. O agente pilota mais do que navega — escreve código, roda testes, propõe soluções. Quando inverte (eu ditando código exato, ele apenas digitando), o resultado sempre piora.</p><h3>Small Releases<span class="hx:absolute hx:-mt-20" id="small-releases"></span>
<a href="#small-releases" class="subheading-anchor" aria-label="Permalink for this section"></a></h3><p>Dos 274 commits, <strong>cada um passa no CI</strong>. Sem exceção. Não existe “commit quebrando que vai ser consertado no próximo”. Cada commit em master é production-ready.</p><p>O CI roda em cada commit: RuboCop (estilo) → bundler-audit (vulnerabilidades de gems) → Brakeman (segurança estática) → testes completos. São ~22 segundos. Parece pouco, mas multiplicado por 274 commits são 100+ minutos de validação automatizada que eu não precisei fazer manualmente.</p><p>A distribuição de commits por dia mostra o ritmo:</p><table><thead><tr><th>Data</th><th>Commits</th><th>Destaque</th></tr></thead><tbody><tr><td>10/fev (seg)</td><td>4</td><td>Scaffold inicial, Discord bot, blog</td></tr><tr><td>11/fev (ter)</td><td>41</td><td>Explosão de features: 7 seções de newsletter, temas, X polling</td></tr><tr><td>12/fev (qua)</td><td>49</td><td>Podcast pipeline, deploy, segurança, market data real</td></tr><tr><td>13/fev (qui)</td><td>29</td><td>Daily digest, scraping resiliente, hardening</td></tr><tr><td>14/fev (sex)</td><td>30</td><td>Integração end-to-end, email hardening, blog deploy</td></tr><tr><td>15/fev (sáb)</td><td>40</td><td>Podcast fine-tuning, cross-app, story management</td></tr><tr><td>16/fev (dom)</td><td>26</td><td>Primeira newsletter real enviada para assinantes</td></tr><tr><td>17/fev (seg)</td><td>31</td><td>Refactoring, Application Commands, anime fix</td></tr><tr><td>18/fev (ter)</td><td>24</td><td>DRY shortcodes, backup job, consolidação</td></tr></tbody></table><p>A “explosão” do dia 2 não é caos — são small releases empilhadas. Cada uma adiciona uma feature, roda CI, está pronta pra deploy. Não é waterfall de 2 semanas seguido de big bang merge. É integração contínua de verdade.</p><h3>Test-Driven Development<span class="hx:absolute hx:-mt-20" id="test-driven-development"></span>
<a href="#test-driven-development" class="subheading-anchor" aria-label="Permalink for this section"></a></h3><p>1.323 testes. 970 no marvin-bot (6 segundos em paralelo), 353 no newsletter (1 segundo em paralelo). Sem esses testes, cada um desses bugs teria ido pra produção. O agente propõe uma mudança, o teste pega a regressão, a mudança é corrigida antes de commitar. O agente é bom em gerar testes — sabe os padrões, sabe os edge cases comuns, sabe a estrutura do Minitest. E os testes que ele gera viram a rede de segurança das mudanças que ele mesmo faz depois. É um ciclo virtuoso: <strong>testes permitem velocidade, velocidade gera mais testes</strong>.</p><h3>Refactoring Contínuo<span class="hx:absolute hx:-mt-20" id="refactoring-contínuo"></span>
<a href="#refactoring-cont%c3%adnuo" class="subheading-anchor" aria-label="Permalink for this section"></a></h3><p>27 commits explícitos de refactoring. Alguns exemplos:</p><ul><li><strong><code>Extract StealthBrowser wrapper</code></strong> — O código de headless browser com stealth patches estava duplicado em 4 clients. Extraiu pra um serviço, 4 clientes ficaram com 5 linhas cada.</li><li><strong><code>DRY section rendering: collapse 5 bubble methods + 7 Hugo shortcodes</code></strong> — 5 métodos de renderização de bolha no <code>MarkdownToHtml</code> que eram copy-paste com cores diferentes colapsados em 1 método parametrizado. 7 shortcodes Hugo delegando pra 1 partial.</li><li><strong><code>Replace market recap LLM generation with Yahoo Finance real data</code></strong> — O LLM inventava números de mercado. Substituí por dados reais do Yahoo Finance + commentary do LLM. Melhor resultado, menor custo.</li><li><strong><code>Replace DuckDuckGo with Brave Search API</code></strong> — DuckDuckGo não tem API estável. Brave Search tem API oficial com 2.000 queries/mês grátis. Troca limpa.</li><li><strong><code>Rework ArticleFetcher: browser-first with anti-detection</code></strong> — Duas reescrituras completas. A primeira tentou HTTP-first com fallback pra browser. A segunda inverteu: browser-first porque a maioria dos links de leitores são SPAs. Cada reescritura manteve os testes passando.</li></ul><p>O refactoring é onde o par de pair programming brilha. Eu digo “esse código tá duplicado, extrai um concern” e o agente faz em 2 minutos o que me levaria 20. Mas <strong>eu</strong> decido o quê extrair e <strong>como</strong> a interface deveria ser. O agente sozinho não refatora — ele empilha código novo em cima do existente.</p><h3>Integração Contínua<span class="hx:absolute hx:-mt-20" id="integração-contínua"></span>
<a href="#integra%c3%a7%c3%a3o-cont%c3%adnua" class="subheading-anchor" aria-label="Permalink for this section"></a></h3><p>O CI já descrito acima: rubocop + bundler-audit + brakeman + testes. Roda em cada commit, em ambas as apps. Brakeman merece destaque:</p><table><thead><tr><th>App</th><th>Controllers</th><th>Models</th><th>Warnings</th><th>Ignored</th></tr></thead><tbody><tr><td>marvin-bot</td><td>6</td><td>8</td><td>0</td><td>0</td></tr><tr><td>newsletter</td><td>10</td><td>5</td><td>0</td><td>2</td></tr></tbody></table><p>Zero warnings de segurança em ambos. Cada um corrigido antes de ir pra produção, no mesmo commit que o CI flaggou.</p><h2>A Anatomia de Uma Feature: Do Pedido ao Deploy<span class="hx:absolute hx:-mt-20" id="a-anatomia-de-uma-feature-do-pedido-ao-deploy"></span>
<a href="#a-anatomia-de-uma-feature-do-pedido-ao-deploy" class="subheading-anchor" aria-label="Permalink for this section"></a></h2><p>Vou pegar um exemplo concreto pra ilustrar como o fluxo funciona na prática. O <code>List-Unsubscribe</code> (commit <code>5950ccc</code>).</p><p><strong>Contexto</strong>: emails de confirmação não chegavam no Gmail. Tudo verde — DKIM, SPF, DMARC, SES aceitando. Mas Gmail jogava no spam silenciosamente.</p><p><strong>Investigação</strong> (eu + agente): pesquisamos. Desde fevereiro de 2024, Gmail exige <code>List-Unsubscribe</code> + <code>List-Unsubscribe-Post</code> em todo email de bulk sender. Sem eles, penaliza o <strong>domínio inteiro</strong> — incluindo emails transacionais.</p><p><strong>Implementação</strong> (agente executa, eu valido): header no <code>SesMailer</code>, endpoint RFC 8058 no <code>UnsubscriptionsController</code> (skip CSRF pra email clients, retorna 200 ao invés de redirect), testes cobrindo ambos os flows.</p><p><strong>CI</strong>: rubocop OK, brakeman pegou o <code>skip_forgery_protection</code> como warning (correto — validamos que é condicional). Testes passam.</p><p><strong>Deploy</strong>: <code>kamal deploy</code>. Em 2 minutos, a correção está em produção. Reputação do domínio leva 1-2 dias pra se recuperar. No dia seguinte, emails de confirmação voltam a chegar.</p><p><strong>Tempo total</strong>: ~25 minutos do “por que o Gmail tá rejeitando?” ao deploy em produção. Sem o agente, seriam horas de leitura de RFC, implementação manual, e esperança de que não esqueci nada.</p><h2>O Que a IA Faz Bem (E o Que Faz Mal)<span class="hx:absolute hx:-mt-20" id="o-que-a-ia-faz-bem-e-o-que-faz-mal"></span>
<a href="#o-que-a-ia-faz-bem-e-o-que-faz-mal" class="subheading-anchor" aria-label="Permalink for this section"></a></h2><p>Depois de 274 commits com um agente de IA, tenho uma noção bem clara dos pontos fortes e fracos:</p><h3>Faz bem:<span class="hx:absolute hx:-mt-20" id="faz-bem"></span>
<a href="#faz-bem" class="subheading-anchor" aria-label="Permalink for this section"></a></h3><ul><li><strong>Boilerplate e scaffolding</strong>: jobs, services, testes, migrations — o agente produz na velocidade de digitação</li><li><strong>Testes</strong>: surpreendentemente bom em identificar edge cases e gerar testes abrangentes</li><li><strong>Refactoring mecânico</strong>: renomear, extrair métodos, mover código entre arquivos — rápido e preciso</li><li><strong>Pesquisa contextual</strong>: “como funciona RFC 8058?” produz resposta acionável em segundos</li><li><strong>Consistência</strong>: segue padrões estabelecidos no projeto (concerns, naming conventions, test structure) sem esquecer</li></ul><h3>Faz mal:<span class="hx:absolute hx:-mt-20" id="faz-mal"></span>
<a href="#faz-mal" class="subheading-anchor" aria-label="Permalink for this section"></a></h3><ul><li><strong>Decisões de arquitetura</strong>: tende a over-engineer. Precisa de freio humano constante</li><li><strong>Conhecimento de domínio específico</strong>: não sabe que o Yahoo faz TLS fingerprinting ou que o VoiceDesign do Qwen produz sotaque europeu</li><li><strong>Opiniões</strong>: suaviza tudo. Um programador medíocre com IA produz código medíocre mais rápido. Um programador experiente com IA produz código bom na velocidade que antes só era possível com equipes.</p><h2>Os Números que Importam<span class="hx:absolute hx:-mt-20" id="os-números-que-importam"></span>

<a href="#isso-%c3%a9-200-user-stories" class="subheading-anchor" aria-label="Permalink for this section"></a></h2><p><img src="https://new-uploads-akitaonrails.s3.us-east-2.amazonaws.com/frankmd/2026/02/66d7f28718285e260f53fe6e_018b4d67589e6f4d2fdf9130502016fb4a75e73a-1200x674.jpg" alt="sprint planning" loading="lazy"></p><p>Olhei os 274 commits e tentei mapear pra user stories no sentido ágil. Nem todo commit é uma story — muitos são fixes dentro da mesma feature, ajustes de prompt, ou cleanup de CI. Mas a contagem conservadora de features distintas, cada uma com critérios de aceitação implícitos (funciona, tem teste, passa no CI, deploya):</p><blockquote><p><strong>Estimativa: ~180-200 user stories.</strong></p></blockquote><p>Isso inclui:</p><ul><li>Cada seção de newsletter (10 geradores distintos com scraping, AI, validação, fallback)</li><li>O pipeline de email (delivery tracking, claiming atômico, recovery, List-Unsubscribe)</li><li>O pipeline de podcast (script LLM, TTS dual-model, assembly, S3, RSS)</li><li>O Discord bot (15+ comandos, embeds, context, multi-turn /ask, daily digest)</li><li>O blog (Hugo + Hextra, 17 shortcodes, RSS podcast, SEO, GA)</li><li>A subscription page (confirmação, temas, LGPD, termos de serviço)</li><li>Infraestrutura (Kamal deploy, Cloudflare, SES config, RunPod, backups)</li><li>21 commits de segurança (SSRF, CSP, rate limiting, encryption, path traversal)</li></ul><p>Em Scrum tradicional com uma equipe de 2-3 devs, uma story bem feita (com code review, QA, deploy) leva em média 1-2 dias. 200 stories × 1.5 dias / 2 devs = <strong>~150 dias de trabalho, ou ~30 semanas em sprints de 2 semanas</strong> (contando planning, review, retro, e o overhead inevitável de coordenação entre pessoas).</p><p>Sendo generoso — equipe sênior, stories bem definidas, sem impedimentos — talvez 10-15 semanas.</p><blockquote><p>Nós fizemos em 8 dias. Uma pessoa e um agente de IA.</p></blockquote><p>Mas — e isso é crucial — <strong>eu não sou um dev qualquer e isso não é um projeto qualquer</strong>. Eu tenho 30 anos de experiência em software. Sei quais decisões importam e quais não. Sei quando parar de engenheirar e shipar. Sei quando o agente está errado antes de ele terminar de gerar o código. E o projeto é solo-developer, sem code review externo, sem QA separado, sem coordenação entre equipes.</p><p>O multiplicador real do agente não é “10x mais código”. É <strong>eliminar o tempo morto</strong>. Sem agente, 70% do meu tempo seria digitando boilerplate, lendo docs de API, escrevendo testes mecânicos, debugando typos. Com agente, esse tempo vira zero e eu foco 100% em decisões de arquitetura, domínio, e qualidade.</p><h2>O CLAUDE.md: A Spec que Evolui<span class="hx:absolute hx:-mt-20" id="o-claudemd-a-spec-que-evolui"></span>
<a href="#o-claudemd-a-spec-que-evolui" class="subheading-anchor" aria-label="Permalink for this section"></a></h2><p>Uma coisa que funciona excepcionalmente bem com agentes de IA é ter um documento vivo que descreve o projeto. O <code>CLAUDE.md</code> do projeto tem 702 linhas e cobre:</p><ul><li>Visão geral da arquitetura</li><li>Stack tecnológico completo</li><li>Todas as variáveis de ambiente</li><li>Estrutura do diretório de conteúdo</li><li>Serviços, jobs e models de cada app</li><li>12 “common hurdles” com soluções documentadas</li><li>14 design patterns do projeto</li><li>Pipeline semanal completo com horários</li><li>Checklist pós-implementação</li></ul><p>Esse documento não foi escrito de uma vez. Ele <strong>evoluiu com o projeto</strong>. Cada vez que descobríamos um hurdle (Yahoo Finance precisa de Chromium, HN RSS muda de formato, LLM suaviza opiniões), documentávamos no CLAUDE.md. Na próxima sessão, o agente já sabe.</p><p>É o equivalente do onboarding doc de uma equipe — mas o “novo membro da equipe” é o agente, e ele lê o doc inteiro em 2 segundos antes de cada interação. O investimento em documentação retorna exponencialmente com agentes de IA porque <strong>eles realmente leem</strong>.</p><p><img src="https://new-uploads-akitaonrails.s3.us-east-2.amazonaws.com/frankmd/2026/02/screenshot-2026-02-20_12-59-38.jpg" alt="claude.md" loading="lazy"></p><h2>As Lições<span class="hx:absolute hx:-mt-20" id="as-lições"></span>
<a href="#as-li%c3%a7%c3%b5es" class="subheading-anchor" aria-label="Permalink for this section"></a></h2><p><strong>1. Vibe coding sem disciplina é protótipo descartável.</strong> 274 commits com CI, testes, security scanning, e small releases é o oposto de vibe coding. É engenharia de software com um copiloto que digita rápido.</p><p><strong>2. TDD é mais importante com IA, não menos.</strong> O agente modifica código com confiança porque tem 1.323 testes como rede de segurança. Sem testes, cada mudança é uma aposta.</p><p><strong>3. O humano decide o quê. O agente decide o como.</strong> Inverta e o resultado piora dramaticamente.</p><p><strong>4. Refactoring contínuo é obrigatório.</strong> O agente empilha código. Se você não poda regularmente — extrair concerns, DRY duplicações, simplificar interfaces — a base de código vira um monólito de 500 linhas por arquivo.</p><p><strong>5. Documentação é investimento com retorno imediato.</strong> Cada hora documentando no CLAUDE.md economiza horas de contexto perdido em sessões futuras.</p><p><strong>6. Small releases são a chave.</strong> Cada commit é production-ready. Se algo der errado, reverte um commit. Se a feature era má ideia, nunca dependeu de outra. Isso só funciona com CI automático.</p><p><strong>7. Segurança não é fase — é hábito.</strong> 21 commits de segurança espalhados por 8 dias, não concentrados numa “sprint de segurança” no final. Brakeman roda em todo commit. Vulnerabilidades são corrigidas no momento que aparecem.</p><p><strong>8. O agente nunca diz “não”.</strong> Isso é um bug, não uma feature. Se você pede algo over-engineered, ele implementa com entusiasmo. Se pede algo inseguro, ele implementa sem reclamar. <strong>Você</strong> é o freio. <strong>Você</strong> é o code review. <strong>Você</strong> é o adulto na sala.</p><h2>O Contra-Exemplo: FrankMD<span class="hx:absolute hx:-mt-20" id="o-contra-exemplo-frankmd"></span>
<a href="#o-contra-exemplo-frankmd" class="subheading-anchor" aria-label="Permalink for this section"></a></h2><p>Tudo que descrevi acima pode soar teórico. <em>“Claro que TDD e refactoring contínuo são importantes”</em> — todo mundo concorda em tese. Então vou provar empiricamente com um contra-exemplo do <strong>mesmo desenvolvedor, com o mesmo agente de IA, duas semanas antes</strong>.</p><p>Antes do M.Akita Chronicles, eu construí o <a href="https://github.com/akitaonrails/FrankMD" target="_blank" rel="noopener">FrankMD</a> — um editor Markdown em Rails, estilo Obsidian/VSCode. 212 commits em 19 dias. Mesmo setup: eu + Claude Code como par de pair programming.</p><p><img src="https://camo.githubusercontent.com/4d7ffcd26d22eb57334017e3b946a10eeb59cacf609edcc8caebf68d03d528b4/68747470733a2f2f6e65772d75706c6f6164732d616b6974616f6e7261696c732e73332e75732d656173742d322e616d617a6f6e6177732e636f6d2f6672616e6b6d642f323032362f30322f73637265656e73686f742d323032362d30322d30315f31342d31332d32392e6a7067" alt="frankmd" loading="lazy"></p><p>A diferença: no FrankMD, eu fiz o que qualquer desenvolvedor faz quando “é só um projetinho pessoal”. Foquei em features. Testes? Depois. Refactoring? Quando necessário. CI? Roda quando lembrar.</p><h3>A Espiral do <code>app_controller.js</code><span class="hx:absolute hx:-mt-20" id="a-espiral-do-app_controllerjs"></span>
<a href="#a-espiral-do-app_controllerjs" class="subheading-anchor" aria-label="Permalink for this section"></a></h3><p>O FrankMD é um SPA-like com Stimulus. No início, todo o JavaScript vivia em um único arquivo: <code>app_controller.js</code>. Aqui está o que aconteceu com ele ao longo dos commits:</p><table><thead><tr><th>Momento</th><th>LOC</th><th>O que aconteceu</th></tr></thead><tbody><tr><td>Commit #1 (inicial)</td><td>506</td><td>Scaffold limpo, editor básico</td></tr><tr><td>Commit #44 (~10 features depois)</td><td>~4.372</td><td>File finder, themes, typewriter, image picker, emoji…</td></tr><tr><td>Commit #54 (pico)</td><td><strong>4.990</strong></td><td>Tudo dentro. AI grammar, video embed, content search…</td></tr><tr><td><strong>Refactor 1</strong>: Extract utilities + image picker</td><td>3.249</td><td>-35%, 6 módulos + 1 controller extraídos</td></tr><tr><td><strong>Refactor 2</strong>: Extract 10 Stimulus controllers</td><td>1.803</td><td>-45%, 10 controllers com testes</td></tr><tr><td>Features crescem de novo…</td><td>2.739</td><td>Mais código empilhado</td></tr><tr><td><strong>Refactor 3</strong>: Extract utility modules</td><td>2.684</td><td>-2%, pequeno</td></tr><tr><td><strong>Refactor 4</strong>: Extract domain controllers</td><td>2.074</td><td>-23%, 4 controllers novos</td></tr><tr><td>Features crescem…</td><td>2.367</td><td>De volta a crescer</td></tr><tr><td><strong>Refactor 5</strong>: Extract autosave/scroll-sync</td><td>1.837</td><td>-22%</td></tr><tr><td><strong>Refactor 6</strong>: Replace custom JS with Rails 8 built-ins</td><td>1.511</td><td>-17%, -383 linhas líquidas</td></tr><tr><td>Estado final</td><td>1.576</td><td>39 controllers + 29 lib modules</td></tr></tbody></table><p>O padrão é claro: <strong>construir-construir-construir-PARAR-refatorar</strong>. O arquivo cresceu 10x em 54 commits, atingiu quase 5.000 linhas, e então precisei de <strong>6 rodadas de refatoração</strong> pra trazer de volta ao aceitável. Cada parada foi um commit grande (centenas de linhas movidas, dezenas de arquivos criados), não um ajuste cirúrgico.</p><p>O CSS seguiu o mesmo padrão: 1.053 linhas num único <code>application.css</code>, até o commit de refactoring que explodiu em 10 arquivos de tema + 9 arquivos de componente.</p><h3>Testes: Antes vs. Depois<span class="hx:absolute hx:-mt-20" id="testes-antes-vs-depois"></span>
<a href="#testes-antes-vs-depois" class="subheading-anchor" aria-label="Permalink for this section"></a></h3><p>No FrankMD, o 2º commit foi “Add comprehensive test suite” — testes de sistema (integração browser). Parece responsável, mas esses testes cobriam <strong>o happy path e nada mais</strong>. Os testes de unidade JavaScript vieram só no commit #52, <strong>depois que o app_controller.js já tinha 5.000 linhas</strong> — porque eu precisava de testes pra refatorar com segurança. Testes retroativos.</p><p>A cobertura Ruby reflete isso: teve que ser empurrada de 77% pra 89% num commit explícito de “Add tests for untested success paths”. Não era TDD — era <strong>preencher buracos depois</strong>.</p><h3>Os Números Lado a Lado<span class="hx:absolute hx:-mt-20" id="os-números-lado-a-lado"></span>
<a href="#os-n%c3%bameros-lado-a-lado" class="subheading-anchor" aria-label="Permalink for this section"></a></h3><table><thead><tr><th>Métrica</th><th>FrankMD</th><th>M.Akita Chronicles</th></tr></thead><tbody><tr><td>Commits</td><td>212</td><td>274</td></tr><tr><td>Dias</td><td>19</td><td>8</td></tr><tr><td>Commits/dia</td><td>11</td><td>34</td></tr><tr><td>Testes</td><td>1.364 JS + ~490 Ruby</td><td>1.323 Ruby</td></tr><tr><td>Coverage Ruby</td><td>~89% (retroativo)</td><td>82-87% (orgânico)</td></tr><tr><td>Ratio teste/código</td><td>~1.2x</td><td>1.52x</td></tr><tr><td>Refactors “pare tudo”</td><td>6 grandes</td><td>0</td></tr><tr><td>Refactors incrementais</td><td>16</td><td>27</td></tr><tr><td>Maior arquivo (pico)</td><td>4.990 LOC</td><td>—</td></tr><tr><td>CI a cada commit</td><td>Não</td><td>Sim</td></tr></tbody></table><p>O número que importa: <strong>commits por dia</strong>. O M.Akita Chronicles teve 3x mais throughput — com TDD, CI, e refactoring contínuo — porque <strong>nunca precisou parar</strong>. Nenhum commit de “parar tudo e refatorar 5.000 linhas em 10 arquivos”. Nenhum momento de “preciso adicionar testes retroativos pra poder mexer nesse código sem medo”.</p><h3>A Lição Concreta<span class="hx:absolute hx:-mt-20" id="a-lição-concreta"></span>
<a href="#a-li%c3%a7%c3%a3o-concreta" class="subheading-anchor" aria-label="Permalink for this section"></a></h3><p>Os 6 refactors grandes do FrankMD não foram “refactoring contínuo”. Foram <strong>cirurgias de emergência em dívida técnica acumulada</strong>. Cada um levou horas — não os 2 minutos do “extrai um concern” descrito acima. E cada um introduziu riscos: quando você move 1.500 linhas de um arquivo pra 10 arquivos novos, a chance de quebrar algo é proporcional ao tamanho da mudança.</p><p>Com TDD e refactoring contínuo, o M.Akita Chronicles nunca acumulou essa dívida. Os 27 refactors são commits pequenos — “Extract StealthBrowser”, “DRY bubble methods” — que levam minutos e são protegidos por 1.323 testes que já existiam quando o refactoring foi feito.</p><p><strong>Mesmo desenvolvedor. Mesmo agente de IA. Duas abordagens diferentes. Resultado: o projeto disciplinado entregou mais, em menos tempo, com menos dor.</strong></p><h2>Conclusão<span class="hx:absolute hx:-mt-20" id="conclusão"></span>
<a href="#conclus%c3%a3o" class="subheading-anchor" aria-label="Permalink for this section"></a></h2><p><img src="https://new-uploads-akitaonrails.s3.us-east-2.amazonaws.com/frankmd/2026/02/41MD3fXWOXL.jpg" alt="xp book" loading="lazy"></p><p>Esse projeto não é um showcase de IA. É um showcase de engenharia de software acelerada por IA. E a prova mais forte é que o <strong>mesmo desenvolvedor com o mesmo agente</strong> produziu resultados radicalmente diferentes dependendo do processo.</p><p>No FrankMD, sem disciplina, o resultado foi previsível: um arquivo de 5.000 linhas, 6 cirurgias de emergência, testes retroativos, e 11 commits por dia. No M.Akita Chronicles, com XP, o resultado foi 34 commits por dia, zero paradas forçadas, 1.323 testes orgânicos, e um sistema em produção em 8 dias. A variável não foi a IA — foi o processo.</p><p>274 commits em 8 dias não acontecem porque o agente é mágico. Acontecem porque Extreme Programming — pair programming, TDD, small releases, refactoring contínuo, integração contínua — funciona tão bem com um par de IA quanto funciona com um par humano. Talvez melhor em alguns aspectos: o agente nunca cansa, nunca discute por ego, nunca diz “mas sempre fizemos assim”, e lê 700 linhas de documentação antes de cada interação sem reclamar.</p><p>O futuro do desenvolvimento não é “IA substituindo programadores”. É programadores que sabem usar IA como ferramenta — com a mesma disciplina que sempre usaram com qualquer outra ferramenta — produzindo em uma semana o que equipes inteiras levam trimestres.</p><p>Não porque a IA é genial. Porque <strong>o processo</strong> é genial. O XP tinha razão desde o começo. Só faltava um par que nunca cansa e digita a 1000 palavras por minuto.</p><p>Lembrem-se:</p><blockquote><p>“A IA é seu espelho, ele revela mais rápido quem você é. Se for incompetente, vai produzir coisas ruins mais rápido. Se for competente, vai produzir coisas boas mais rápido.” - by Akita</p></blockquote>
